# Integrate original Browse changes

## Scope and merge

- Use only for an explicit request to sync official Browse and validate the local extension in both Chrome and Opera. For sync-only work, use `.agents/skills/browse-sync-upstream/SKILL.md` only when its documented destination matches the requested target.
- Work in this checkout and merge `upstream/dev` into the branch checked out when this skill starts. Record that branch and HEAD; normally do not switch branches or create a branch/worktree, reset, or rewrite commits. If HEAD is `stage`, follow the mandatory exception: fetch the latest `origin/stage` and create a task branch from it in this checkout; merge and commit on that branch, never directly on `stage`. Do not push unless explicitly asked.
- Verify the `upstream` URL is `https://github.com/anomalyco/browse.git`, the current branch, and that no unrelated Git operation is active. Prefer a clean worktree. If it contains only explicitly identified, task-owned pending changes, record their paths and contents and prove the fetched upstream delta does not modify those paths (including checking that untracked paths are absent from the incoming tree); preserve and verify those changes across the merge. If any change is unrelated, overlapping, or cannot be proven safe, stop before merging.
- Fetch upstream, record its exact `dev` SHA, inspect incoming commits/authors, and check CI for the tip. If it is already an ancestor of HEAD, do not create an empty merge; continue with the requested checks and report that no merge was needed. Resume an existing merge only after verifying its parents.
- Merge the recorded SHA without committing. Resolve conflicts semantically, inspect changes from both sides even when auto-merged, and preserve both upstream behavior and the fork's TypeScript MCP/relay, group controls, CLI, tab ownership, and handoff contracts. Keep the unpacked extension identity and checkout-backed `dist` installation. Borrow only `browse-sync-upstream`'s toolchain versions, test recipes, disposable-export/release-check handling, and build-identity guidance. Do not follow its branch-selection, merge, or commit-target/commit steps; this skill owns those decisions and commits on its verified target, applying the `stage` exception above.

## Checks, build, and activation

- Run focused checks for changed boundaries on the resolved tree. Fix confirmed integration defects and rerun affected focused checks.
- After the build/reload and applicable browser checks below, use the single `review-and-fix` gate. After a clean review and completed live checks (or a documented capability stop), run the required terminal suites once on the final tree, following global test policy and the recipes listed in `browse-sync-upstream`. Do not normalize the tested merge tree. Commit all task-scoped changes on the verified target branch, or on the task branch created by the `stage` exception; if no merge or other task-scoped change was needed, do not create an empty commit.
- Use only the README's dependency, build, and guarded reload steps; skip its branch-switch and pull commands. Update the local build ID only when runtime code changes. Check the isolated relay is idle, then reload with each browser's current ID. Verify the extension ID, loaded path, and exact running build in both browsers. Never force a reload or disturb another session; stop and report if safe activation is unavailable.

## Chrome and Opera verification

- Before browser work, read the canonical `browser-interactions` and `browse-agent` skills, plus `browser-interactions/references/browse.md` (Browse adapter), `browser-interactions/references/local-group-controls.md`, and `browser-interactions/references/browser-selection-and-efficiency.md`. Discover current tool schemas and `status`; use the connected Chrome and Opera IDs explicitly. Keep each browser in its existing window and preserve user focus and selection.
- Test Chrome and Opera sequentially. In each, create one uniquely owned, correctly titled grouped session with the group collapsed and verified before page work. Create exactly five owned tabs in that same group, adding and navigating them one at a time; verify membership and collapse after tab changes. Never navigate concurrently or use ungrouped tabs.
- Use five separate tabs for these base checks: navigate and verify URL/title; inspect a grounded snapshot; click a grounded link and verify its destination; fill and verify a safe form (submit only a deterministic test/demo form); and verify tab-ID targeting by reading the expected page from the correct tab while the other tabs remain open. Use safe, non-authenticated test pages and no real-world submissions.
- If grouped creation or collapse cannot be verified in either browser, delete that exact session and verify its targets are gone, then stop that browser's test. Do not switch browsers, fall back to ungrouped tabs, or engineer around a missing browser API. The local group-controls reference records an Opera grouping failure and no documented Opera `tabGroups` API as of 2026-11-22; treat this as an unsupported capability unless new verified evidence changes it, not as a code defect or a passing test.
- After any fix, rerun affected automated checks, rebuild/reload when runtime code changed, and repeat affected browser scenarios. Delete each owned session after its five-tab run and verify all tabs and the session are absent. Report Chrome and Opera results separately, including any unsupported capability; never claim cross-browser success when either browser's grouping gate failed.
